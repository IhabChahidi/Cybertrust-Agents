Request lifecycle

This is what happens inside one call to POST /api/v1/generator/verified-claims. Foundation-Sec generates and grounds a claim first; only if it actually produces one does the claim enter the orchestrator's state machine (MCPServer.process_claim(), mcp_server/orchestrator.py:176).

Short-circuit that matters: if Foundation-Sec can't find corporate evidence linked to the question (only reference intel like a CVE description, no matching case/ticket/asset), it returns INSUFFICIENT_EVIDENCE on its own — by contract, this never reaches the Verifier or Validator at all. Reference knowledge alone is never treated as proof of organizational exposure.

Deterministic rule scan flags things like a "closed" status with no proof field, or a conclusion resting on a single evidence item.

STAGE 5

SCORING

A 0–100 MCP Score is computed from fixed point tables — severity, exposure, impact, evidence quality, verification, contradiction penalty — yielding a risk_level.

A pure policy function reads the verification status + risk_level and applies fixed routing rules (plus optional local overrides) to decide what happens next.

STAGE 7

Invariant guards double-check the routing (e.g. a risk-level floor), then the claim is routed toward a human CISO decision — this stage never auto-approves anything.

COMPLETED

The full result — claim, verification_result, mcp_score, validation_decision, ciso_routing, and the transitions list — is assembled and journaled to disk.

02 / diagram

System topology — who runs where

The short version: there is no separate Verifier or Validator container. Only two things in this stack are actual network services — ChromaDB and llama.cpp. Everything else, including the whole orchestrator, Verifier, and Validator, is plain Python running inside the single generator-api container.

Why there's no "Verifier container" or "Validator container" to find: both are selected by mcp_server/llm_roles/factory.py's build_verifier() / build_validator() and instantiated once inside MCPServer.__init__. With llm_mode="mock" (what we've been running), the Verifier is MockVerifier — pure Python contradiction-checking, zero network calls — and the Validator is PolicyValidator, which calls no LLM either: it reads config/policy_rules.yaml (baked into the image) and applies fixed rule tables. The only way a Verifier ever makes a network call is llm_mode="llama", which talks to a local Ollama server — a completely different dependency from the llama-generator container, and not defined anywhere in docker-compose.yml.
